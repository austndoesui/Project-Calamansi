## First Cactus userspace root

`tools/cactus-init.S` is a minimal ARM64 static diagnostic process with native XNU syscalls, a PID1 banner, and periodic `/dev/console` heartbeat. `tools/build_cactus_init.py` builds it locally using GNU ARM64 binutils and `tools/mkinit.py`'s ad-hoc Mach-O signing; its ELF input is checked for wrong architecture or unresolved relocations. Generated `shim/out/cactus/stage55-init/cactus-init.macho` (16,635 bytes) SHA256 `d187f6f1529b9290dfcd64d6923ce2a59e30f6d9fdb463970728744d806e9991`.

`tools/stage27_pack_kernel.py --stage55-live-fb --ramdisk ...` appends that Mach-O as the root (11th segment, 32,768-byte VM reservation), selects `rd=md0`, and adds the ADT `RAMDisk` memory map. The built-in mockfs in the inherited XNU patches can recognize a raw Mach-O as a root. This does not establish that it will mount or execute on Cactus. A critical **relocation bug was fixed**: `shim/prepare_stage18_payload.py` previously moved kernel segments but left `/chosen/memory-map/RAMDisk` at old PA `0x724bc000`. It now pins the source to exactly one segment and relocates the ADT pointer to `0x824bc000` along with the payload. Stage55's boot_args location is `0x824c8000`.

**Static route audit (2026-10-25):** Examined actual local XNU source under `/home/lapdq/xnu-cactus`. `iokit/bsddev/IOKitBSDInit.cpp` reads `/chosen/memory-map/RAMDisk`, calls `mdevadd()`, and resolves `rd=md0` using `mdevlookup()`. The patched `bsd/miscfs/mockfs/mockfs_vfsops.c` accepts the raw Mach-O magic during `mountroot`; `mockfs_vnops.c` maps `/sbin/launchd` to that image, and `bsd/kern/kern_exec.c` has `/sbin/launchd` in its PID1 search list. This confirms the intended pathname and root-device *code path*; it does not prove runtime device-tree publication, successful mount or execution. The diagnostic binary currently parks if opening `/dev/console` fails, so **an absent PID1 banner alone would not prove that the executable never ran**. Determine progress from preceding on-screen BSD and root-mount checkpoints as well.
