# Stage75 — PID1 executable argument read and loader checkpoints

The corrected Stage74 physical-memory-copy kernel reached `ST71 PID1 execve entered` on the Redmi6A native XNU framebuffer (PID1 still orange). That shows the real execve call started after PID1's first argv page was populated, but not that a Mach-O file was opened or executed.

### Functional CACTUS-only change

Stage75 XNU patch `xnu/patches/0110-cactus-pid1-exec-read-stage75.patch` uses the same real pinned PID1 scratch page that Stage74 wires. `cactus_init_read()` verifies that the current process is PID1 and the source lies fully within that scratch page, locates each real page in the current PID1 task pmap (`pmap_find_phys`) and copies its physical-memory alias (`phystokv`) into kernel argument buffers. Reads from other processes or outside the scratch page still use ordinary XNU `copyin`. `cactus_init_readstr()` reads bounded NUL-terminated strings via the same mechanism. Only three critical exec path consumers are redirected: `exec_save_path` for the launchd pathname, `exec_add_user_string` for argv strings, and `copyinptr` for argv pointer table entries (32-/64-bit). This is a bootstrap workaround for the early TTBR0 copyin problem, not general ARM64 userspace support; other user memory operations may require proper pmap bring-up.

Added grouped framebuffer checkpoints inside PID1 `__mac_execve` (clone begin, clone returned, image activate begin, activate result) and in `exec_activate_image` (path read, VFS namei, executable header read). Existing PID1 `getpid() == 1` green-bar gating preserved. Source generated in `shim/out/cactus/stage75-source/bsd/kern/kern_exec.c`.
